## テンプレートからの逸脱について

`/test-design` のテンプレートは Web API を前提としており、「同時接続数」「RPS」「SQL インジェクション」「トークン有効期限」といった項目を含む。本アプリは**ネットワーク通信を一切行わないローカルデスクトップアプリ**であり、HTTP エンドポイント・データベース・認証機構をいずれも持たない。該当セクションは本アプリで意味のある内容に置き換え、置き換えた旨を各節に明記した。

なお serena / context7 MCP は本セッションで未接続のため、Stage 2 と同様に Web 検索で代替した (設計書 §調査手段に関する注記を参照)。

## 1. テスト概要

### 1.1 テスト目的

本アプリのテストは、通常のアプリケーションと目的の重心が異なる。**「クラッシュしないこと」よりも「同じ入力から必ず同じ出力が出ること」の保証に最大の比重を置く。**

理由は 2 つある。

1. **書き出し結果の再現性が製品価値そのもの** — 制作用途 (要件の主用途) では、同じプロジェクトを 2 回書き出して結果が違えば、そのツールは信用できない。設計では決定性のために複数の判断 (変調値の tick 由来算出、シードの決定的導出、オフライン解析テーブル、トランスポートのアンカー方式) を行っており、これらが実際に機能していることの検証が最重要
2. **同期の破綻は静かに起きる** — 音映像のずれや位相の飛びは例外を投げない。テストで能動的に測らない限り気づけず、気づいたときには原因箇所の特定が困難になっている

したがって本テスト設計の中心は **プロパティテスト (性質テスト)** であり、個別の入出力例よりも「どんな入力でも成り立つべき不変条件」を検証する。

副次的な目的として以下を置く。

- リソースリーク (`VideoFrame` / `ImageBitmap` / GPU テクスチャ) の検出。設計書 §10.2 で「後付けが困難」とした項目の実効性担保
- 非機能要件 (NF-1〜NF-8) の測定と、目標値の妥当性検証
- Phase 0 の PoC 8 項目を**測定手順の定義された受け入れテスト**として実行可能にすること

最後の点について補足する。設計書 §10.4 は PoC 項目を「実測する」と書いたが、手順と合否判定を定義していない。本書 §4.3 でこれを埋める。**PoC は判断のための調査であると同時に、後で回帰させないための恒久テストでもある。**

### 1.3 テスト環境と階層

**テストを 5 層に分け、実行コストと実行頻度を対応させる。**この分割が本テスト設計で最も重要な構造的判断である。層 1 を厚くし、GPU や実時間を要する層は薄く保つことで、開発サイクルを維持する。

| 層 | 名称 | 実行環境 | 所要時間 | 実行頻度 | 件数目標 |
|---|---|---|---|---|---|
| **1** | 純ロジック | Vitest (Node)。GPU・音声デバイス不要 | < 30 秒 | ファイル保存ごと / commit 前 | 400+ |
| **2** | GPU | Vitest + Electron レンダラ (実 WebGPU) | 1〜3 分 | commit 前 | 60+ |
| **3** | 音声 | Vitest + Electron レンダラ (`OfflineAudioContext`) | 1〜2 分 | commit 前 | 50+ |
| **4** | E2E | Playwright (Electron ドライバ) | 5〜10 分 | Phase 完了時 / 週次 | 15+ |
| **5** | 非機能・計測 | 専用ハーネス + 手順書 | 10 分〜2 時間 | Phase 完了時 / 夜間 | 20+ |

**層 3 が実デバイス不要である点は重要。** `OfflineAudioContext` は実時間より高速に、かつ決定的にレンダリングでき、`AudioWorklet` も動作する。音声処理の正しさはハードウェアなしで検証できる。実デバイスが要るのは「出力チャンネル数の実測」など層 5 の一部に限られる。

#### 依存関係とモック方針

| 依存 | テストでの扱い |
|---|---|
| `AudioContext` の時刻 | **`FakeClockSource` を注入。** Transport のテストは実時間に一切依存させない。1 時間分の経過を数ミリ秒で検証する |
| `AudioContext.getOutputTimestamp()` | 層 1 では固定値を返すスタブ。較正ロジックの検証に用いる |
| WebGPU | 層 1 ではモックしない。**シェーダ実行を伴わない部分を分離して層 1 に置く** (§2.5 の設計制約) |
| WebCodecs | 層 1 では `FakeClipPlayer` (指定 tick に対応する単色フレームを返す) を注入 |
| FFmpeg | 層 1〜3 ではモック。層 4〜5 で実バイナリを使用 |
| ファイルシステム | 層 1 は `memfs`。層 4 は一時ディレクトリ |
| MIDI デバイス | 合成 `MIDIMessageEvent` を投入 |
| ディスプレイ | 層 4 では単一ディスプレイ環境でも通るよう、2 画面目は任意扱いにする |

#### テスト用メディアの生成

**テスト用メディアはリポジトリにコミットしない。** FFmpeg で生成するスクリプトを用意し、`pretest` で一度だけ生成してハッシュキャッシュする (§3.1)。動画をバイナリでコミットするとリポジトリが肥大化し、生成条件も追えなくなる。

例外はクロマキーのゴールデン画像 (数十 KB の PNG)。これは期待値そのものなのでコミットする。

| ID | 性質 | 検証内容 | 試行数 |
|---|---|---|---|
| TMP01 | **往復一致** | `toTicks(toSeconds(t)) ≈ t` (誤差 < 0.5 tick) | 10,000 |

| TMP04 | **連続性** | テンポ変更点の前後で秒がジャンプしない (左極限 = 右の値) | 1,000 |

| TMP07 | **スナップの近接性** | `\|snap(t) - t\| ≤ グリッド幅` | 5,000 |

TMP08 は「速いが分かりにくい二分探索実装」を「遅いが自明な実装」と突き合わせる方式で、最適化によるデグレを確実に捕まえる。

### 4.4 A/V 同期の測定 (NF-3)

**測れるものと測れないものを区別する。**

| ID | 対象 | 手法 | 合格基準 |
|---|---|---|---|
| PF201 | **書き出し結果の同期** | 生成物をデコードしてフラッシュ位置とクリック位置を機械検出 (シナリオ 5) | 全マーカーで ≤ 1 フレーム。**完全に自動化可能** |
| PF202 | **内部クロックのずれ** | 30 分再生中、毎フレーム `positionForFrame()` の結果と音声側の実位置を記録し、乖離を集計 | 乖離 ≤ 2 フレーム相当 |
| PF203 | 知覚的な同期 | — | **内部計測では原理的に測定できない** |

PF203 について。ディスプレイやプロジェクタの内部遅延はアプリから取得する手段がなく、スピーカーまでの経路も同様である。厳密に測るには画面と音を外部のカメラ・マイクで同時収録して解析する必要があり、常設テストとしては現実的でない。

**したがって、知覚的な同期は「A/V オフセット設定で人が合わせる」という設計上の解決に委ねる** (設計書 §2.2.3)。本テストで保証するのは「内部クロックが正確であること」(PF202) と「書き出し結果が正確であること」(PF201) の 2 点であり、**この 2 つが正しければ、残る誤差は定数オフセットのみで、ユーザー調整で吸収できる**という構成になっている。この限界を明記しておく。

## 6. テスト実行計画

### 6.1 実行順序とタイミング

| タイミング | 実行する層 | 所要時間 | 失敗時 |
|---|---|---|---|
| ファイル保存時 (watch) | 層 1 の関連ファイルのみ | < 3 秒 | エディタに表示 |
| commit 前 (pre-commit フック) | 層 1 全部 + lint + typecheck | < 60 秒 | commit 中止 |
| push 前 / 日次 | 層 1〜3 | < 6 分 | 通知 |
| Phase 完了時 | 層 1〜5 (PF401 の 2 時間ソーク含む) | 〜3 時間 | Phase 未完了とする |
| 夜間 (任意) | 層 5 の長時間項目 (PF402 の 8 時間ソーク) | 8 時間 | 翌朝レポート確認 |

**層 1 を 30 秒以内に保つことを死守する。**ここが遅くなると誰も実行しなくなり、テストスイート全体が形骸化する。層 1 が重くなってきたら、それは GPU や I/O への依存が漏れ込んでいる兆候として扱う。

### 6.2 合格基準

#### 必須ゲート (1 つでも落ちたら Phase 完了としない)

| # | ゲート | 内容 |
|---|---|---|
| 1 | **決定性テスト全通過** | MDP01〜07、AUP01、CUP01〜03、シナリオ 4 |
| 2 | **リソース収支テスト全通過** | RL001、RL003、RL005 |
| 3 | 該当 Phase の機能テスト全通過 | 優先度 High 以上のケース |
| 4 | 該当 Phase の非機能目標達成 | NF-1〜NF-8 のうち該当するもの |
| 5 | セキュリティテスト全通過 | §5 の High 以上 |

#### カバレッジ目標

**カバレッジ率は補助指標であり、合格ゲートにはしない。** 90% を満たしていても決定性テストが 1 本落ちていれば不合格、という位置づけを明確にする。カバレッジは「テストを書き忘れている領域を見つける道具」として使う。

| 領域 | 行 | 分岐 | 備考 |
|---|---|---|---|

| `engine/audio/backend` | 80% | 75% | |
| `main/media`, `main/ipc` | 80% | 75% | |
| `ui/**` | 50% | — | E2E でカバー |
| **全体** | **80%** | **75%** | 参考値 |

#### 静的検査

CLAUDE.md の規約を lint ルールとして機械的に強制する。

| 規約 | 実現方法 |
|---|---|
| `any` 禁止 | `@typescript-eslint/no-explicit-any: error` |
| `unknown` 禁止 | カスタムルールまたは `no-restricted-syntax` で型注釈中の `unknown` を検出。**zod 内部の使用は除外** |
| `class` 禁止 | `no-restricted-syntax` で `ClassDeclaration` を禁止。`src/shared/errors.ts` のみ除外 |
| 単位型の混同 | branded type により型検査で自動的に防がれる |

## 7. リスクと対策

| # | リスク | 影響度 | 発生確率 | 対策 |
|---|---|---|---|---|
| TR-1 | **GPU ベンダ差でゴールデンテストが落ちる** | High | High | 完全一致を要求せず、許容誤差 (≤ 2/255) で比較。それでも不安定なら PSNR/SSIM 閾値へ切替。基準画像は開発機で生成し、機種変更時は差分を目視レビューして更新 |
| TR-2 | WebCodecs のデコーダ挙動が環境依存 | High | High | 上限値をテストにハードコードせず、**PC004 で測定した値を設定として持つ**。テストは「設定値を超えない」ことを検証する |

| TR-5 | ゴールデン画像の保守コスト | Medium | Medium | 生成スクリプトを用意。意図的な変更時は一括再生成し、差分画像を目視確認する手順を決めておく |
| TR-6 | **テストが実装の内部構造に依存して壊れやすくなる** | High | Medium | プロパティテストと入出力ベースのテストを主軸にする。内部メソッドを直接叩くテストを書かない |
| TR-7 | E2E が不安定 (flaky) になる | Medium | High | 固定待機を使わず条件待ちにする。特に**ポート受け渡しは 100 回連続実行で安定性を確認** (S001-R) |

## 8. テスト自動化戦略

### 8.1 自動化の範囲

| 分類 | 自動化 | 対象 |

**手動が 3 項目に収まっている点が本設計の狙い。** 特に「書き出し結果の A/V 同期」(PF201) を機械検出可能にしたことで、本来手作業になりがちな検証が自動化できている。

### 8.2 CI 構成

本プロジェクトは個人利用であり CI サーバーを常設しない前提だが、以下の構成を推奨する。

| 実行方式 | 対象 | 備考 |
|---|---|---|
| **ローカル pre-commit フック** | 層 1 + lint + typecheck | 主戦場。husky + lint-staged |
| **ローカル `npm run test:full`** | 層 1〜4 | push 前 / Phase 完了時 |
| **GitHub Actions (windows-latest)** | **層 1 のみ** | GPU なしでも動く範囲。リポジトリを公開する場合に有効 |
| ローカル夜間バッチ | 層 5 の長時間項目 | タスクスケジューラ |

**ホストランナーには GPU がないため、層 2 (WebGPU) は原則 CI で実行できない。** Dawn のソフトウェアバックエンド (SwiftShader 等) で動かす選択肢はあるが、実行が著しく遅く、かつ実 GPU と結果が微妙に異なるため、**ゴールデンテストの実行環境としては信頼できない**。層 2 はローカル実行に限定するのが現実的な判断。

## 9. テスト設計で判明した設計の未確定事項 【2026-08-19 全件決着済み】

テストケースを書き起こす過程で、設計書が決めきれていない挙動が 8 件見つかった。**いずれも「どちらでもよいが、決めないと実装者が場当たりに選んでしまう」種類のもの**であり、実装前に決着させた。

**全 8 件とも下表の「推奨」どおりに確定した。** 確定版の挙動仕様は `.tmp/design.md` §10.5 を正とする (以降の実装はそちらを参照)。本節は検討経緯とテストケース対応の記録として残す。

| ID | 項目 | 選択肢 | 推奨 → **確定** | 関連テスト |
|---|---|---|---|---|
| **D-1** | **負の tick を許すか** | (a) 許す: カウントイン・プリロールが自然に書ける (b) 禁止: 0 未満は 0 にクランプ | **(a) 許す。** DAW 機能のカウントイン (F-A1) で必要になり、後から許可制に変えるのは全変換ロジックに影響する | TM204, TR101 |

| **D-3** | Transport の rate = 0 / 負値 | (a) 0 は一時停止と等価、負は拒否 (b) 両方許可し逆再生を実装 | **(a)。** 設計上の逆再生はクリップ単位 (F-V4) であり、トランスポート全体の逆再生は要件にない | TR104, TR105 |
