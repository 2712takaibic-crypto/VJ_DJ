- 前提文書: `.tmp/requirements.md` / `.tmp/design.md` / `.tmp/test_design.md`

## テンプレートからの逸脱について

`/tasks` のテンプレートは「Phase 1: 準備・調査 / Phase 2: 実装 / Phase 3: 検証・テスト / Phase 4: 仕上げ」という汎用の 4 段構成を想定している。本プロジェクトは要件定義の時点で **Phase 0〜7 の独自フェーズ**を定義しており、各フェーズが「単体で価値のある成果物」を持つよう設計されている (要件定義 §5、リスク R-6 への対策)。

そのため**フェーズ番号はプロジェクト独自のものを使う。**テンプレートの 4 段構成は、各フェーズ内部の「準備 → 実装 → 検証」という並びとして反映した。

また「検証・テストを最後にまとめる」構成も採らない。テスト設計 §6.1 で定めたとおり、**テストは各タスクの完了条件に組み込む**。各タスクには対応するテスト ID を明記し、それが通ることを完了条件とした。

## 概要

| 項目 | 値 |
|---|---|
| 対象範囲 | **Phase 0〜4** (設計書が実装可能な粒度で設計した範囲) |
| 総タスク数 | **92** (Phase 0: 22 / Phase 1: 25 / Phase 2: 16 / Phase 3: 13 / Phase 4: 16) |
| 推定作業時間 | **約 320 時間** (集中作業時間ベース) |
| 優先度 | 高 (Phase 0〜1) / 中 (Phase 2〜3) / 中低 (Phase 4) |
| 対象外 | Phase 5 (DJ) / Phase 6 (DAW) / Phase 7 (高度化) — 設計書が拡張点のみ定義しているため、各フェーズ着手時に別途分解する |

### 粒度に関する方針

**Phase 0 と Phase 1 はコミット単位 (1〜4 時間) まで分解した。Phase 2〜4 はタスク単位に留め、チェック項目は主要なもののみとした。**

理由は、Phase 0 の PoC 結果 (§4.3 の 8 項目) が Phase 2 以降の前提を変えうるためである。具体的には、PC003 (出力チャンネル数) が不合格なら音声周りの構成が変わり、PC004 (同時デコード本数) の実測値はレイヤー数上限を通じて UI 設計に影響する。**確定していない前提の上に細かい計画を積んでも捨てることになる。**

Phase 2 着手時に、そのフェーズを改めてコミット単位へ分解する。

### 工数見積もりについて

上記 320 時間は**手が止まらなかった場合の集中作業時間**であり、調査・試行錯誤・手戻りを含まない。WebGPU / WebCodecs / AudioWorklet はいずれも扱いに慣れが要る API であり、初見の箇所では見積もりの 1.5〜2 倍かかることを見込んでおくのが現実的。

週 15 時間の作業なら Phase 0〜1 (約 158 時間) で**おおよそ 3〜4 か月**、Phase 4 まで通すと **7〜9 か月**が目安になる。

## 注意事項

- **各タスクはコミット単位で完結させる。**完了条件を満たさないまま次に進まない
- **タスク完了時に必ず lint / typecheck / 該当層のテストを実行する**
- 各タスクの完了条件に書かれたテスト ID は `.tmp/test_design.md` に対応する。**テストを後回しにしない**

- 設計書 §10.2 の「後付けが極めて困難な 7 項目」は、該当タスクで必ず組み込む。速度を優先して飛ばさない
