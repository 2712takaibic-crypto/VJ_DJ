# VJ/DJ 統合ツール 要件仕様書

- 作成日: 2026-08-18
- ステータス: Stage 1 (Requirements) — 初版・レビュー待ち
- 元要望: `plan.txt`

---

## 1. プロジェクト概要

### 1.1 目的

個人利用を前提とした、VJ・DJ・楽曲制作を単一のタイムラインとトランスポート上で扱える統合ツールを開発する。市販ソフト (Resolume / rekordbox / Ableton Live) の完全な代替ではなく、**「映像制作を主軸に、音楽的な同期を第一級で扱えるツール」** を目指す。

### 1.2 確定した前提条件

| 項目 | 決定 | 仕様への影響 |
|---|---|---|
| 技術スタック | TypeScript + Electron | Web Audio / WebCodecs / WebGPU / Web MIDI を基盤とする。ASIO・VST は直接扱えない |
| 最優先の柱 | **VJ (映像)** | Phase 1 の成果物は映像合成エンジンとする |
| 主用途 | **制作・書き出し中心** | 決定性のあるオフラインレンダリングを優先。リアルタイム要求は緩和 |
| ハードウェア | MIDIコントローラ / DJコントローラ(ジョグ付) / 外部オーディオIF / 2画面目出力 | MIDIマッピング層、マルチch出力、独立出力ウィンドウが必須 |

### 1.3 スコープに関する重要な判断

`plan.txt` の4項目は、そのままでは商用ソフト3本分の規模になる。本仕様では以下の方針で分解する。

**共通基盤を先に作り、その上に3つの柱を段階的に載せる。**

```
                 ┌──────────┐  ┌──────────┐  ┌──────────┐
                 │  VJ 機能  │  │  DJ 機能  │  │ DAW 機能 │
                 └────┬─────┘  └────┬─────┘  └────┬─────┘
                      └─────────────┼─────────────┘
        ┌─────────────────────────────────────────────────┐
        │  共通基盤                                        │
        │  ・Transport / Clock (BPM・拍・タイムライン)      │
        │  ・Media Engine (デコード・エンコード・解析)      │
        │  ├ Project Store (非破壊編集・状態管理)          │
        │  └ Control Surface (MIDIマッピング)              │
        └─────────────────────────────────────────────────┘
```

この基盤、特に **Transport/Clock** の設計を誤ると3つの柱すべてが作り直しになる。ここが本プロジェクト最大の設計上の勘所である。

## 2. 機能要件

優先度: **P0** = MVPに必須 / **P1** = 初期リリースに必要 / **P2** = 将来拡張

### 2.1 共通基盤

#### F-C1: トランスポート / マスタークロック (P0)

- 再生・停止・ループ・シーク・録音待機の統一トランスポートを持つ
- 時間表現は **秒ではなく tick (PPQ = 960)** を正とし、テンポマップ経由で秒に変換する
- テンポマップは可変BPM (テンポチェンジ) を保持できること
- **マスタークロックは必ずオーディオクロック (`AudioContext.currentTime`) とする**
  - 理由: `performance.now()` / `requestAnimationFrame` はオーディオデバイスのクロックと必ず乖離する。長時間の再生・書き出しで音ズレを起こす
- 映像の描画は、各フレームの提示時刻に対応するトランスポート位置を問い合わせて状態をサンプリングする
- 拍・小節単位のイベントバスを提供し、VJエフェクト・DAWシーケンサ・DJループが共通で購読する

#### F-C2: プロジェクト管理 (P0)

- プロジェクトファイル形式は JSON (将来的な肥大化に応じて SQLite への移行を検討)
- **完全非破壊編集**: 元メディアは一切改変しない。編集内容は参照 + パラメータで表現する
- メディアはパス + コンテンツハッシュで参照し、パス変更時の再リンク機能を持つ
- 自動保存とバージョン履歴 (直近N世代のスナップショット)
- Undo/Redo (コマンドパターンによる操作履歴)

#### F-C3: メディア取り込み (P0)

- 対応入力
  - 音声: mp3 / ogg / wav / flac / aac / m4a
  - 映像: mp4 / mov / webm / mkv / avi
  - 静止画: png / jpg / webp (アルファ付きpng含む)
- 取り込み時に自動でメタデータ解析 (長さ・解像度・fps・コーデック・チャンネル数)
- **プロキシ生成 (P0)**: 取り込み時に再生用の中間ファイルを生成する
  - 映像: 全フレームIフレームの H.264 (fMP4) に変換。任意解像度 (既定 1080p)
  - 理由: Long-GOP のまま扱うとシーク・スクラブが実用にならず、複数レイヤー同時再生でデコード帯域が破綻する
  - 元ファイルは書き出し時に使用する (プロキシ/オリジナルの切り替え)
- 波形・サムネイルのキャッシュ生成 (バックグラウンドジョブ)

#### F-C4: 音楽解析 (P1)

- BPM 検出とビートグリッド生成 (小節頭の推定を含む)
- 手動でのビートグリッド補正 (オフセット調整・BPM上書き)
- キー検出 (Camelot / Open Key 表記で表示)
- 音量解析 (ピーク・LUFS)、ダウンビート・オンセット検出
- 解析は取り込み時にワーカースレッドでバッチ実行し、結果をプロジェクトにキャッシュ

#### F-C5: コントロールサーフェス (P1)

- MIDI入力デバイスの列挙と接続
- **MIDIラーン**: UI上の任意パラメータに対し、操作したMIDIメッセージを割り当てる
- マッピングはプロファイルとして保存・切り替え可能 (デバイスごと)
- 対応メッセージ: Note / CC (絶対値・相対値) / Pitch Bend
- ジョグホイールは相対CCとして扱い、速度・慣性モデルを介して再生位置へ反映 (P2)
- MIDIクロック送受信 (外部機器との同期) (P2)

### 2.2 VJ 機能 【最優先】

#### F-V1: レイヤーコンポジタ (P0)

- 無制限のレイヤースタック (実用上は8〜16レイヤーを性能目標とする)
- レイヤーソース種別:
  - 動画クリップ / 静止画 / カメラ入力 / 単色・グラデーション / ジェネラティブ (シェーダ) / 他レイヤーの出力
- レイヤーごとのプロパティ: 不透明度・ブレンドモード・変形 (位置/拡縮/回転/アンカー)・クロップ・可視性・ソロ
- ブレンドモード: Normal / Add / Screen / Multiply / Overlay / Difference / Lighten / Darken (最低8種)
- レイヤーのグループ化とグループ単位のエフェクト適用 (P1)
- マスク: 別レイヤーの輝度またはアルファをマットとして使用 (P1)

#### F-V2: クロマキー / 背景合成 (P0)

**要望の中核。ナイーブな実装では実用に耐えないため、以下の要素を必須とする。**

- キーカラーのスポイト指定
- **CbCr平面上の色距離**による判定 (単純なRGB閾値ではなく)
- **内側/外側の二重閾値** によるソフトエッジ生成 (完全透過域と半透過域を分離)
- **スピル抑制 (Despill)**: 被写体の輪郭に残る緑かぶりを除去
- **マットのチョーク / フェザー**: 収縮・膨張とぼかしによる境界調整
- マット単独表示モード (調整用)
- ライトラップ (背景色の輪郭へのなじませ) (P1)
- 非グリーンバック素材向けのAIセグメンテーション切り抜き (P2)

#### F-V3: エフェクト (P1)

- レイヤー単位およびマスター出力へのエフェクトチェーン
- 基本セット: 色調補正 (露出/コントラスト/彩度/色相/カーブ)・ブラー・シャープ・グロー・歪み・フィードバック・ストロボ・スライス/グリッチ・カレイドスコープ
- **すべてのエフェクトパラメータは BPM同期可能** であること
  - LFO変調 (波形・レート指定を 1/4拍・1拍・1小節などの音楽的単位で)
  - ビート/小節トリガ
  - 音声解析値 (帯域別レベル・オンセット) による変調 (P1)
- エフェクトはWGSLで記述し、宣言的なパラメータ定義からUIを自動生成する

#### F-V4: 映像タイムライン編集 (P0)

- レイヤー = トラックとして時系列に並ぶタイムラインUI
- クリップの配置・トリム・分割・移動・複製・リップル削除
- キーフレームによるパラメータのアニメーション (補間: リニア / ベジェ / ステップ / ホールド)
- **拍・小節へのスナップ** (音楽グリッドへの吸着)
- クリップ単位の再生速度変更・逆再生・ループ

#### F-V5: 出力 (P0)

- **操作画面と出力画面の分離**
  - 出力は独立ウィンドウとして任意のディスプレイへフルスクリーン表示
  - 出力解像度・アスペクト比はプロジェクト設定に従い、ディスプレイ解像度と独立
- コントロールウィンドウにはプログラムプレビューを表示 (低解像度・低フレームレートで可)
- 出力へのテストパターン表示 (位置合わせ用)
- NDI / Spout 出力 (P2)

#### F-V6: ライブトリガ (P1)

制作中心とはいえ、素材の作り込みに必要な最小限のライブ操作を持つ。

- クリップをグリッド状に配置し、ボタン/MIDIパッドで即時トリガ
- トリガのクオンタイズ (次の拍/小節/4小節から発火)
- 操作内容をタイムラインへ記録し、後からタイムライン編集に変換できること

### 2.3 DJ 機能

#### F-D1: デッキ (P1)

- 2デッキ (将来4デッキに拡張可能な設計)
- 波形表示 (全体波形 + スクロールする拡大波形、周波数帯域による着色)
- **タイムストレッチ / ピッチシフト独立制御**
  - キーロック (テンポ変更時に音程を保つ) — DJ機能の必須要件
- ビートグリッドに基づく **シンク** (デッキ間のテンポ・位相合わせ)
- ホットキュー (最低8点)、ビート単位のループ (1/8〜32拍)、ループロール
- ピッチフェーダー (±8/16/50%)、ネガティブなし

#### F-D2: ミキサー (P1)

- チャンネルごとの 3バンドEQ (キル可能) + ゲイン + フィルタ (LPF/HPF一体型ノブ)
- クロスフェーダー (カーブ切り替え: スムーズ/シャープ)
- チャンネルフェーダー、マスターゲイン、レベルメーター
- センドエフェクト: リバーブ / ディレイ / エコー / フランジャー / ビートリピート (すべてBPM同期)

#### F-D3: ヘッドホンキュー — **スコープ外 (2026-08-19 確定)**

当初は「マルチチャンネルオーディオIFの ch3/4 へキュー信号を独立送出」を P2 として想定していたが、
**ユーザーがオーディオインターフェースを保有しておらず、購入予定もないため対象外とする。**

PC003 の実測でも、この環境の出力デバイスは 5 件すべて 2ch であり、
`ChannelMergerNode` による master/cue 分離は成立しない (`.tmp/poc-results.md` §PC003)。

DJ 機能 (Phase 5) は **1 系統出力・キューなし**を前提に設計する。
次に繋ぐ曲の頭出しは、波形表示とビートグリッドによる視覚的な確認で代替する
(制作・書き出し中心の用途では実用上の支障は小さい)。

将来オーディオIF を導入した場合の再検討は、`npm run poc:audio` の再実行から始めればよい。

#### F-D4: ライブラリ (P1)

- トラック一覧、BPM・キー・ジャンル・レーティングによるソート/フィルタ
- **ハーモニックミキシング支援**: 現在のトラックとキーが調和するトラックのハイライト
- プレイリスト / クレート
- 再生履歴の記録

### 2.4 DAW 機能

#### F-A1: シーケンサ (P2)

- MIDIトラックとオーディオトラック
- ピアノロールエディタ (ノート入力・編集・ベロシティ・クオンタイズ)
- ステップシーケンサ (ドラム打ち込み向け)
- MIDI入力のリアルタイム録音、メトロノーム、カウントイン

#### F-A2: 音源 (P2)

- **サンプラー**: サンプルのキーマッピング、ADSR、フィルタ、ピッチ、ワンショット/ループ、スライス
- 基本シンセ (減算方式: OSC×2 + フィルタ + エンベロープ + LFO)
- ドラムマシン (パッドごとにサンプル割当)

#### F-A3: ミキシング (P2)

- トラックごとの音量・パン・ミュート・ソロ
- インサートエフェクト (EQ / コンプレッサ / ディストーション / コーラス / リバーブ / ディレイ)
- センド/リターンバス、マスターバス

**制約: VSTプラグインはサポートしない (§4.4 参照)**

### 2.5 書き出し 【制作用途の中核】

#### F-E1: オフラインレンダリング (P0)

- **決定性を最優先**: 固定タイムステップで1フレームずつ合成し、リアルタイム性に依存しない
- 映像出力: mp4 (H.264/H.265) / mov (ProRes) / webm (VP9)
- 解像度・fps・ビットレート・カラースペースの指定
- 音声出力: wav / mp3 / aac (ミックスダウン)
- 映像+音声の多重化、範囲指定書き出し (イン/アウト点)
- 進捗表示とキャンセル、レンダリングキュー (P1)

#### F-E2: ライブキャプチャ (P1)

- 演奏中の出力をそのまま録画 (品質より即時性優先)
- 同時に操作ログを記録し、後からタイムラインとして再構成できること

#### F-E3: 音声のみの書き出し (P1)

- DJミックスの録音・書き出し (キューポイント情報を含むCUEシート生成)

## 3. 非機能要件

| ID | 項目 | 目標値 |
|---|---|---|
| NF-1 | 映像プレビュー | 1080p / 8レイヤー / エフェクト各2段で 60fps 維持 |
| NF-2 | 音声レイテンシ | 往復 30ms 以下 (制作用途としては十分。ライブDJには不足 — §4.2) |

| NF-5 | プロジェクト読込 | 100クリップ規模で 3秒以内 |
| NF-6 | 安定性 | 2時間の連続稼働でメモリリーク・クラッシュなし (GPUリソースの明示的解放が必須) |
| NF-7 | 書き出し速度 | 1080p/30fps で実時間の3倍以内 |
| NF-8 | 対象環境 | Windows 11 / 個人利用のため単一環境に最適化してよい |

## 4. 技術要件

### 4.1 全体構成

```
┌────────────────────────────────────────────────────────┐
│ Main Process (Node.js)                                 │
│  ・ウィンドウ/ディスプレイ管理  ・ファイルI/O           │
│  ・FFmpeg 子プロセス制御 (取り込み・書き出し)           │
│  ・ネイティブアドオン境界 (将来のASIO/Spout)            │
└───────────────┬────────────────────────────────────────┘
                │ IPC (contextBridge / MessagePort)
    ┌───────────┴───────────┬─────────────────────┐
    ▼                       ▼                     ▼
┌─────────────┐   ┌──────────────────┐   ┌──────────────┐
│ Control Win │   │ Output Window    │   │ Worker Pool  │
│ (React UI)  │   │ ★レンダエンジン   │   │ ・音楽解析    │
│ ・タイムライン│  │ ・WebGPU 合成     │   │ ・波形生成    │
│ ・プレビュー  │  │ ・WebCodecs デコ  │   │ ・サムネイル  │
│ ・ミキサー   │   │ ・AudioWorklet   │   │              │
└─────────────┘   └──────────────────┘   └──────────────┘
```

**重要な設計判断**: WebGPU のデバイス/テクスチャは Electron のウィンドウ間で共有できない。したがって **レンダリングエンジンは出力ウィンドウ側に置く**。コントロールウィンドウは状態差分を IPC で送り、プレビューは出力ウィンドウ側で縮小読み戻し (`copyTextureToBuffer` → 480p程度) したものを Transferable な ArrayBuffer で受け取って 2D Canvas に描画する。この方式の実効帯域と遅延は Phase 0 で PoC により実測すること。

### 4.2 オーディオ

| 領域 | 採用技術 | 備考 |
|---|---|---|
| 再生・ルーティング | Web Audio API | ノードグラフはWeb Audio、カスタムDSPはAudioWorklet |
| カスタムDSP | AudioWorklet (128サンプル量子) | EQ・フィルタ等の基本はBiquadFilterNodeで足りる |
| タイムストレッチ | **signalsmith-stretch** を WASM 化して AudioWorklet 内で実行 | 代替: SoundTouch (LGPL)。**Rubber Band は GPL** のため配布時は要注意 |
| 音楽解析 | **essentia.js** (WASM) | BPM・ビートトラッキング・キー・オンセット・HPCP を一括で賄える |
| オフラインミックスダウン | OfflineAudioContext | AudioWorklet も動作する。実時間より高速にバウンス可能 |
| MIDI | Web MIDI API | Electron側で `setPermissionRequestHandler` による `midi`/`midiSysex` 許可が必要 |

**ASIO について (重要)**

Chromium は Windows 上で WASAPI を使用し、**Web Audio から ASIO ドライバへはアクセスできない**。制作中心の用途では WASAPI で十分だが、以下の2点は制約となる。

1. レイテンシ: 共有モードで往復 15〜30ms 程度。ライブでのスクラッチ操作には体感的に不足する
2. ヘッドホンキュー: 2系統独立出力が必要

2 については、**マルチチャンネルデバイスが1つのデバイスとして見えていれば Web Audio 内で解決できる可能性が高い**。`AudioContext.destination.channelCount` をデバイスの最大チャンネル数に設定し、`ChannelMergerNode` でマスターを ch1/2、キューを ch3/4 へルーティングする。この可否は使用するオーディオIFに依存するため、**Phase 0 で実機検証すること**。

不可の場合、または低レイテンシが必須になった場合は、**RtAudio / miniaudio をNode-APIアドオン化したネイティブオーディオバックエンド**への差し替えが必要になる。これは大きな設計変更になるため、**音声エンジンは最初からインターフェースで抽象化し、バックエンドを差し替えられる構造にしておく**こと。

### 4.3 映像

| 領域 | 採用技術 | 備考 |
|---|---|---|
| リアルタイムデコード | **WebCodecs `VideoDecoder`** | GPUデコードが効く。`VideoFrame` をそのままGPUテクスチャへ転送可能 |
| デマックス | **mp4box.js** | WebCodecs は demux を持たないため必須。プロキシを fMP4 に統一すればこれで足りる |
| 取り込み・書き出し | **ネイティブ FFmpeg** (子プロセス) | MKV/AVI/HEVC/ProRes 等の長い裾野はここで吸収。プロキシ生成もここ |
| 合成 | **WebGPU (WGSL)** | レイヤーごとにテクスチャ、エフェクトはping-pongによる複数パス |
| ブレンドモード | フラグメントシェーダで実装 | WebGPU の固定機能ブレンドでは Overlay/Difference 等を表現できない |
| エンコード | 書き出し時はネイティブFFmpegへ生フレームをstdin投入 | WebCodecs `VideoEncoder` より形式の自由度が高く、音声多重化も一括で行える |
| ライブ録画 | `canvas.captureStream()` + MediaRecorder | F-E2用の簡易経路 |

**プロキシ方式について**: 4K の Long-GOP 素材を複数レイヤーで同時再生・スクラブするのは、この構成では現実的でない。取り込み時に **全フレームIフレーム化した中間ファイル**を作ることで、シーク性能とデコード負荷の両方が解決する。将来的にさらなる多レイヤー性能が必要なら、**HAP コーデック** (GPUで直接展開できるVJ標準コーデック) をネイティブアドオンで導入する余地を残す。

### 4.4 フレームワーク / ライブラリ

| 領域 | 候補 | 判断 |
|---|---|---|
| デスクトップシェル | **Electron** (Tauri ではなく) | Chromium を同梱するため WebCodecs/WebGPU の挙動が確定する。Tauri は WebView2 のバージョン差異で挙動が読めない。またネイティブアドオンとマルチディスプレイ制御が容易 |
| UI | React + TypeScript | タイムライン等の重い部分は Canvas 描画で自前実装 |
| 状態管理 | Zustand または Jotai | 高頻度更新 (トランスポート位置) はストア外に置き、購読で配る |
| ビルド | Vite + electron-vite | |
| テスト | Vitest / Playwright (Electron) | |

**採用しないもの**

- **VST/AU プラグイン**: ネイティブのプラグインホストが必要で、この構成では実現できない。代替は **WAM (Web Audio Modules v2)** だがエコシステムは小さい。**DAW機能は自作音源のみ**という前提を最初から受け入れること
- **Pioneer 等の HID モード DJ コントローラ**: プロトコルが非公開。**MIDIモードで動作する機種のみ対応する**

### 4.5 検証が必要な項目 (Phase 0 で PoC)

1. **ウィンドウ間プレビュー転送**: 出力ウィンドウ→コントロールウィンドウへの縮小フレーム転送の帯域・遅延・CPU負荷
2. **マルチチャンネル出力**: 手持ちのオーディオIFで Web Audio から ch3/4 へ独立出力できるか
3. **WebGPU 有効性**: 使用する Electron バージョンで WebGPU が既定有効か、フラグが必要か (バージョン依存のため要実測)
4. **多レイヤーデコード**: 1080p All-Intra を同時8本デコードした際のフレーム落ち
5. **AudioWorklet 内タイムストレッチ**: 2デッキ同時実行時の CPU 負荷とドロップアウト
6. **オーディオクロック同期**: 30分再生後の映像と音声の乖離量

## 6. リスクと対策

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| R-1 | ウィンドウ間でGPUテクスチャを共有できず、プレビュー転送がボトルネックになる | 大 | Phase 0 で実測。最悪の場合プレビューを 360p/15fps に落とす、または NDI 経由に切り替える |
| ~~R-2~~ | ~~Web Audio でヘッドホンキューを実現できない~~ | — | **解消 (2026-08-19)。**機材を保有しないためキュー自体をスコープ外とした (F-D3)。リスクではなく確定した制約になった |
| R-3 | タイムストレッチのCPU負荷が想定を超える | 中 | 品質モードの切替 (プレビューは低品質・書き出しは高品質)。デッキ数の制限 |
| R-4 | 多レイヤー再生でデコードが破綻 | 大 | プロキシ方式で緩和済み。さらに必要なら HAP 導入 |
| R-5 | VST非対応により音作りの幅が制約される | 中 | 受容する。DAW機能はスケッチ用と位置づけ、本格的な音作りは既存DAWとのステム受け渡しで補う |
| R-6 | 3つの柱すべてを作り切れず中途半端に終わる | **大** | フェーズごとに単体で完結する価値を持たせる。Phase 3 で一度「完成品」にする |
| R-7 | ライセンス (FFmpeg GPL版・Rubber Band GPL) | 小 | 個人利用の範囲では問題ない。配布する場合は LGPL版FFmpeg + 非GPLなストレッチャに差し替える |
